# 发布流程（RELEASING）

本仓是**单向派生产物**：从内部生产版派生出通用版，派生过程由可复跑的迁移脚本完成
（「逐字节拷贝 → 按替换对定点替换，任一条不命中则整轮不写盘」）。**公开稿的改进要手工、逐条回灌生产版**，
绝不能让派生脚本把公开稿的改动静默覆盖。

## 一、版本号怎么定（SemVer）

| 改动类型 | 版本动作 | 例子 |
|---|---|---|
| 配置项默认值变了 / 已有环境变量语义变了 / 退出码语义变了 | **主版本** `X.0.0` | 数据根默认值改变 |
| 新增症状、新增 CLI 参数、新增环境变量、报告新增小节 | **次版本** `.Y.0` | 新增「冷盘落点表」注入 |
| 修错别字、改注释、修内部实现 bug（行为不变） | **修订** `.0.Z` | 补一个漏掉的 import |
| 只改文档 | 修订（可不发版） | README 补一节 |

> 判定有疑问时**向上取**：宁可多升一位，也不要让使用者以为「换个版本什么都不用改」。

## 二、CHANGELOG 规范

- 固定四组：`Added` / `Changed` / `Fixed` / `Breaking`（没有就不写）；
- **`Breaking` 必须写「怎么恢复旧行为」**（哪个环境变量、设成什么值）；
- 面向使用者写（"你看到的行为变了"），不要写代码内部细节；
- 未发布的改动先进 `## [Unreleased]`，发版时改名为 `## [X.Y.Z] - YYYY-MM-DD` 并新开一个 Unreleased 段。

## 三、发布前检查单

- [ ] `node scripts/verify-source.mjs .` → 命中 0（**先注入本机标识再跑**，见下）
- [ ] `node scripts/verify-source.mjs . --positive-control <确信存在的串>` → 打印「阳性对照通过」
      （**不做这一步的"命中 0"不可信**：规则可能整条哑火）
- [ ] `node _test/test-firstaid-run.mjs`（E2E）/ `test-drill.mjs` / `test-rollback-index.mjs`
      —— 失败项要么修，要么在交付说明里逐条归因（含**改动前副本的对照实验**）
- [ ] 所有 `.mjs` 过 `node --check`；`.ps1` 过 PowerShell 解析器
- [ ] README 的配置表与 `lib/runtime-config.mjs` 实际读取的变量**逐一对照**（新加变量必须同时进表）
- [ ] `CHANGELOG.md` 已写；`Breaking` 段附恢复方式
- [ ] 许可：**三处齐改** —— `LICENSE` 全文、README 许可节、`package.json` 的 `license` 字段
- [ ] 打包白名单（`package.json` 的 `files`）与实际要发布的内容一致

### 脱敏扫描怎么跑（关键）

标识词表**只走环境变量**，一个字都不写进仓库：

```bash
BUILD_MACHINE_NAMES='<机器名1>;<机器名2>' \
BUILD_USER_NAMES='<用户名>' \
BUILD_PERSONAL_TERMS='<私人称呼1>;<私人称呼2>' \
BUILD_INTERNAL_TERMS='<内部组件名>;<项目代号>' \
BUILD_LAYOUT_ROOTS='<本机目录布局名>' \
node scripts/verify-source.mjs .
```

- 多值分隔符 `,` `;` `|` 三者等价（只认逗号会让竖线写法**静默失效**，"0 命中"其实是"没扫"）；
- 脚本会**用注入规则再扫它自己**并打印结果行 —— 扫描器自身不许夹带任何标识；
- `--positive-control <串>` 用来证明规则真的在跑。

## 四、发布步骤

```bash
# 1. 从内部版重新派生（迁移脚本 + 替换对，见交付报告里的归档目录）
# 2. 自检 + 单测（上面的检查单）
# 3. 提交与打 tag（组件仓三段式）
git add -A
git commit -m "chore: release vX.Y.Z"
git tag -a vX.Y.Z -m "vX.Y.Z"
git push -u origin main --tags
```

## 五、实测踩过的坑（照抄别重踩）

1. **替换串里的 `$&`**：做"定点替换"的脚本若用 `String.replace(old, new)`，`new` 里的 `$&`/`$1`
   会被当成模式展开，直接把目标文件写坏。**一律用 `split(old).join(new)` 做字面替换。**
2. **链式替换对**：第二条替换对的 `old` 取自第一条的 `new` 时，"先全量检查、后统一写盘"的实现会
   把第二条判成「未命中」——**要按声明顺序边检查边应用**。
3. **同一区域被两条替换对先后修改**：后一条的 `new` 会覆盖前一条，导致幂等检查误报；
   正确姿势是**每次从源文件重新派生**，而不是在已改过的副本上二次替换。
4. **扫描器规则里的日期/常量假阳性**：8 位十六进制规则会把 `20260910`、`86400000` 判红 ——
   加过滤（必须含 a–f）之后才可用。**假红比漏判更危险**，它会训练人忽略红色。
5. **`.cmd` 文件禁中文**：cmd.exe 按系统代码页解析 UTF-8 无 BOM 的批处理会把中文字节拆坏命令；
   要放中文就写进 `.ps1`（UTF-8 **带 BOM**）或用 Node 脚本。
